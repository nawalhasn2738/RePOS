## Suggested ordering and handovers

1. **Shared-approved behavior first:** Nawal consolidates source observations and open decisions; Iman supplies money/date/payment examples and Hamna supplies history/data mappings. Keep observed defects separate from corrected expected behavior.
2. **Safe characterization prerequisite:** Nawal's setup proposal and Hamna's isolated fixtures enable later authorized execution. Shared owns the integrated comparison suite; none is run in this phase.
3. **Contracts before implementation:** Nawal defines initial seams/access strategy; Iman specifies validated sale/input/output commands and results; Hamna specifies durable commit/import/reconciliation contracts. Each output has a distinct owner.
4. **Highest integrity work:** coordinate FO-01/FO-02/FO-03/FO-09. Iman must not treat separate successful repository calls as a committed sale; Hamna must not implement a competing domain/discount policy.
5. **Incremental separation/policy/security:** FO-04 through FO-11 proceed with agreed contracts and tests; do not defer authentication or validation until release. Move table concerns deliberately, preserving view refresh and accepted valid operations.
6. **Acceptance:** Shared verifies all nine workflow groups and approved numerical/history cases; Hamna demonstrates relationship/failure reconciliation; Nawal supplies safe handover. Unknown financial history cannot be “fixed” by fabricated backfill.

## Preservation boundaries

- Preserve the seven tabs' accepted workflows, add/list scope, product-ID basket input, highest-eligible discount behavior pending approved changes, immediate replenishment scope and optional receipt/console feedback.
- Keep all 90 original assets unchanged, including binary tools/report, tests, IDE configuration and identical vendor files. No file is obsolete merely because its future responsibility changes.
- The proposed ER model does not authorize selecting an engine or implementing a schema. No current sale-cashier link, external vendor order, label/hardware printer, payment gateway, refund or generic CRUD is invented.
- Transaction/item bidirectionality may remain if justified; removing the domain-to-manager constant dependency and moving persistence serialization are separate decisions.
- All future verification depends on isolated execution and open requirements decisions. Runtime failures, exact GUI outcomes, supported JDK and original Word report contents remain unverified.

## What requires review before code changes

Approve money/point rates and sentinel mapping, date boundaries/timezone, valid inputs, credentials/account migration, sale shortage/atomic/retry behavior, history repair/unknown values, vendor scope and output timing. Source-derived payment state concerns require experiments; they are not a claim of a demonstrated exploit.
